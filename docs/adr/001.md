- **Número do ADR:** 001
- **Título:** Comunicação de amostras com Message Buffer
- **Data:** 2026-10-29
- **Responsável:** Luís Oliveira, Margarida Teixeira
- **Estado:** Aceite

## Contexto
O projeto recolhe temperatura e humidade do sensor DHT20 e grava as amostras num ficheiro no cartão microSD. A aquisição e o armazenamento são executados em tarefas FreeRTOS distintas. A escrita no cartão pode demorar, pelo que a tarefa de aquisição não deve depender da duração de cada operação de ficheiro. O README do projeto regista que foi escolhido um Message Buffer para transferir as amostras entre estas tarefas.

## Decisão
Foi decidido utilizar um Message Buffer do FreeRTOS como canal de comunicação entre a tarefa que produz as amostras do DHT20 e a tarefa que as consome para armazenamento. Cada mensagem transporta uma estrutura `dht20_data_t` com temperatura e humidade. O buffer é criado para acomodar oito amostras, incluindo o espaço de controlo exigido por mensagem.

## Justificativa
- O Message Buffer permite transferir mensagens de tamanho variável entre tarefas sem partilhar diretamente a estrutura de dados.
- A tarefa de aquisição pode entregar uma amostra e prosseguir, enquanto a tarefa de armazenamento trata da escrita no cartão.
- O mecanismo já faz parte do FreeRTOS usado pelo projeto, sem introduzir uma dependência adicional.
- O bloqueio na receção permite à tarefa de armazenamento aguardar por novas amostras sem polling ativo.

## Alternativas consideradas
- Fila (Queue) do FreeRTOS: adequada para transferir estruturas de tamanho fixo e uma alternativa simples. Foi sorteado o Message Buffer, embora as amostras atuais tenham tamanho fixo.
- Variáveis globais partilhadas e mutex: exigiriam sincronização explícita e poderiam acoplar a aquisição ao consumo, além de não manter naturalmente várias amostras pendentes.
- Escrita direta no cartão pela tarefa de aquisição: simplificaria a passagem de dados, mas faria a aquisição esperar pelas operações de armazenamento.

## Consequências
- A aquisição e a persistência ficam desacopladas, permitindo que a tarefa de armazenamento consuma as amostras de forma independente.
- O buffer tem capacidade limitada; se ficar cheio, o envio pode falhar e a aplicação tem de definir como tratar essa amostra. Atualmente, o código verifica se o envio foi completo e regista erro.
- O produtor e o consumidor têm de concordar no formato e no tamanho da estrutura enviada.
- A criação e a inicialização do buffer têm de ocorrer antes de iniciar as tarefas que o utilizam.
- A integração deverá ser verificada em hardware para confirmar o comportamento sob atrasos de escrita no cartão.
